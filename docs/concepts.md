# 개념

상태: 이 문서는 현재 구현을 기술한다

## 역할과 경계

Sendway가 답하는 질문은 하나입니다 — **"이 메시지를 이 목적지로 보냈는가, 그 결과는 무엇인가."**

| | 내용 |
|---|---|
| 아는 것 | 채널, 요청에 실려 온 목적지(이메일 주소·디바이스 토큰), 메시지 내용, 테넌트의 채널 자격증명, 발송 결과 |
| 모르는 것 | 수신자가 누구인지(신원·계정), 왜 보내는지(어떤 업무 이벤트인지), 수신 동의 여부, 목적지 목록의 보관 |

호출하는 서비스는 "누구에게, 왜, 언제"를 결정하고, Sendway는 "어떻게 전달하는가"만 맡습니다. 어떤 기능이 Sendway의 몫인지는 두 질문으로 가릅니다.

1. 발송을 정확하고 안전하게 수행하는 데 필요한가.
2. 모든 호출 서비스가 똑같이 재구현하게 되며, 그 사실을 발송 서비스만 볼 수 있는가.

둘 중 하나에 해당하면 Sendway의 몫입니다 — 채널 프로토콜 연동, 발신 자격증명 보관, 재시도, 중복 발송 방지, 발송량 제한, 결과 기록이 여기에 속합니다. 둘 다 아니면 호출 서비스의 몫입니다 — 수신자 조회, 발송 시점 결정, 수신 동의 확인, 발송 결과에 따른 후속 업무 처리가 여기에 속합니다.

## 입력과 출력

- **입력(명령)**: 발송 요청 하나 — 채널, 목적지, 내용. 요청은 그 자체로 완결되며, Sendway는 이전 요청이나 호출 서비스의 상태를 참조하지 않습니다.
- **출력(사실)**: 두 가지입니다. 요청이 접수되었다는 사실(응답의 메시지 ID)과, 그 메시지의 발송 결과(성공 또는 실패와 사유). 접수는 요청에 대한 응답으로 바로 알 수 있고, 발송 결과는 메시지 ID로 조회합니다.

## 테넌트(Tenant)

Sendway를 호출하는 서비스 하나. 인증(API 키), 채널 자격증명 오버라이드, 발송량 제한, 발송 결과 조회 범위의 단위입니다. 인스턴스 하나를 여러 테넌트가 함께 쓰며, 테넌트 추가는 관리 API 호출로 끝납니다(재배포 없음).

테넌트는 호출 서비스 자신을 가리킬 뿐, 그 서비스가 가진 조직·사용자 구조를 표현하지 않습니다.

## 채널(Channel)

메시지가 전달되는 매체. 현재 이메일과 앱 푸시가 있습니다.

## 어댑터(Adapter)

채널을 실제 발송 프로토콜에 연결하는 구성요소. 이메일은 SMTP와 Microsoft Graph, 앱 푸시는 Firebase Cloud Messaging 어댑터가 있습니다. 한 채널에 어댑터가 여럿이면 테넌트에 등록된 자격증명이 어느 쪽을 쓸지 정합니다.

## 배포 형태

독립 실행형 서비스(컨테이너 이미지)로 배포해 HTTP API로 호출합니다. 여러 서비스가 공유하는 중앙 인스턴스와 특정 환경 전용의 독립 인스턴스는 같은 이미지이며, 차이는 설정뿐입니다. .NET 프로젝트에 라이브러리로 직접 포함하는 SDK 경로는 아직 없습니다.
