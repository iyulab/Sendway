# 운영

Sendway를 직접 띄워 운영할 때 필요한 절차입니다 — 설치, 업그레이드, 백업과 복구, 장애 대응, 비밀값 교체, 감사 로그. 대기열 상태와 로그가 무엇을 뜻하는지는 [아키텍처](architecture.md)의 「운영」에 있습니다.

## 설치

Sendway는 컨테이너 이미지 하나로 돕니다. 필요한 것은 PostgreSQL 데이터베이스 하나와, 암호화 키를 둘 디렉터리(볼륨) 하나입니다.

```bash
docker build -f src/Sendway.Service/Dockerfile -t sendway-service .
docker run -d --name sendway -p 8080:8080 \
  -v sendway-data:/data \
  -e ConnectionStrings__Sendway="Host=<db-host>;Database=sendway;Username=<user>;Password=<password>" \
  -e Sendway__AdminApiKey="<충분히 긴 무작위 값>" \
  sendway-service
```

- **데이터베이스** — 빈 데이터베이스를 만들어 두면 Sendway가 시작할 때 스키마를 만들고, 이후 버전의 마이그레이션도 시작할 때 적용합니다. 그 계정에는 스키마를 바꿀 권한이 필요합니다.
- **`/data` 볼륨** — Data Protection 키 링(`/data/dp-keys`)이 여기 있습니다. 저장된 채널 자격증명·웹훅 서명 비밀값·발송 대기 중인 메시지 내용이 이 키로 암호화되므로, 이 볼륨은 컨테이너보다 오래 살아야 하고 데이터베이스와 함께 백업합니다(「백업과 복구」).
- **관리자 키** — 없으면 `/admin/*`가 모두 `401`이라 테넌트를 만들 수 없습니다.
- **공용 채널 자격증명** — 테넌트가 따로 등록하지 않았을 때 쓰는 발신 계정입니다. 설정(`Smtp__*`, `Fcm__CredentialsJson`, `Solapi__*`)으로 주거나, 설정 없이 띄운 뒤 `PUT /admin/credentials/{channel}`로 등록합니다(「비밀값 교체」). 둘 다 없는 채널로 온 발송은 접수된 뒤 재시도 끝에 `Failed`가 됩니다.
- 띄운 뒤 `curl http://localhost:8080/admin/queues -H "X-Admin-Key: <관리자 키>"`가 `200`이면 관리자 키와 데이터베이스 연결이 함께 확인된 것입니다. 첫 테넌트를 만들고 보내 보는 방법은 [README](../README.md)의 「보내 보기」.

데이터베이스 없이 잠깐 띄워 보는 SQLite 경로(`Sendway__DatabaseProvider=Sqlite`)는 로컬 시험용입니다 — 파일이 네트워크 볼륨에 있으면 잠금이 안정적이지 않고, 스키마를 마이그레이션 없이 만들기 때문에 이후 버전으로 올릴 수 없습니다.

### 설정

환경변수 이름은 설정 키의 `:`를 `__`로 바꾼 것입니다(`Sendway:RateLimit:RequestsPerMinute` → `Sendway__RateLimit__RequestsPerMinute`). 시간 값은 `00:00:30` 형식입니다.

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `ConnectionStrings:Sendway` | — | PostgreSQL 연결 문자열. 필수 |
| `Sendway:AdminApiKey` | — | 관리 API 키. 없으면 관리 API를 쓸 수 없음 |
| `Sendway:DataProtectionKeyPath` | `/data/dp-keys`(이미지) | 암호화 키 링 디렉터리 |
| `Smtp:*` · `Fcm:*` · `Solapi:*` | — | 공용 채널 자격증명. 있으면 시작할 때마다 이 값이 저장되고 API로는 바꿀 수 없음 |
| `Sendway:RateLimit:RequestsPerMinute` | `60` | 테넌트당 분당 요청 수 |
| `Sendway:RateLimit:Enabled` | `true` | `false`면 한도 없음 |
| `Sendway:Delivery:MaxAttempts` | `5` | 메시지 하나의 발송 시도 횟수 |
| `Sendway:Delivery:AttemptTimeout` | `00:00:30` | 시도 하나의 제한 시간 |
| `Sendway:Delivery:RetryBaseDelay` · `RetryBackoffFactor` | `00:00:05` · `6` | 재시도 간격(5초, 30초, 3분, 18분) |
| `Sendway:Delivery:Concurrency` | `4` | 한 인스턴스가 동시에 보내는 메시지 수 |
| `Sendway:Delivery:WorkerEnabled` | `true` | `false`면 접수만 하고 발송(메시지·웹훅)은 다른 인스턴스에 맡김 |
| `Sendway:Webhooks:MaxAttempts` · `AttemptTimeout` · `Concurrency` | `6` · `00:00:15` · `2` | 웹훅 전달의 같은 값들 |

### 여러 인스턴스

같은 데이터베이스를 보는 인스턴스를 여럿 띄워도 됩니다 — 발송 대기열은 데이터베이스에서 조건부 갱신으로 집어 가므로 한 메시지를 두 인스턴스가 함께 보내지 않습니다. 이때 지킬 것:

- **키 링을 함께 씁니다.** 모든 인스턴스가 같은 `Sendway:DataProtectionKeyPath`(공유 볼륨)를 봐야 합니다. 인스턴스마다 키 링이 따로면 한 인스턴스가 접수한 메시지 내용을 다른 인스턴스가 읽지 못해, 재시도 끝에 `Failed`가 됩니다.
- **요청 한도는 인스턴스마다 셉니다.** 한도 상태가 메모리에 있으므로 인스턴스가 N개면 테넌트의 실제 한도는 대략 N배입니다.
- 마이그레이션은 여러 인스턴스가 동시에 시작해도 데이터베이스 잠금으로 한 번만 적용됩니다.

## 업그레이드

새 이미지로 바꿔 띄우면 됩니다. 시작할 때 아직 적용되지 않은 마이그레이션이 적용되고, 그 뒤에 발송을 시작합니다.

1. **올리기 전에 백업합니다** — 마이그레이션은 되돌려지지 않으므로, 문제가 생겼을 때 돌아갈 곳은 백업입니다.
2. 그 버전에 새 마이그레이션이 있는지 봅니다(`src/Sendway.Core/Migrations/`에 새로 생긴 파일). 표나 nullable 열을 **추가하기만** 하는 마이그레이션은 옛 버전 인스턴스가 아직 도는 동안 적용돼도 문제가 없습니다 — 무중단으로 갈아 끼울 수 있습니다. 열이나 표를 **지우거나 이름을 바꾸는** 마이그레이션이면 옛 인스턴스를 먼저 멈추고 올립니다.
3. 정상 종료(`SIGTERM`)되는 인스턴스는 진행 중이던 발송 시도를 횟수에 넣지 않고 대기열로 돌려놓습니다. 강제로 끝난 인스턴스가 붙잡고 있던 메시지는 그 시도의 제한 시간에 30초를 더한 만큼(기본 1분) 기다렸다가 다른 인스턴스가 다시 집어 갑니다. 어느 쪽이든 접수된 메시지는 데이터베이스에 있으므로 재시작으로 잃지 않습니다.
4. 올린 뒤 `GET /admin/queues`가 `200`이고 `oldestDueSeconds`가 커지지 않는지 봅니다.

**되돌리기** — 옛 이미지로 다시 띄웁니다. 그 사이 적용된 마이그레이션이 추가만 했다면 옛 버전은 새 스키마에서 그대로 동작합니다(모르는 열은 쓰지 않습니다). 다만 새 버전에서 쓰기 시작한 기능은 옛 버전에서 동작하지 않습니다 — 예를 들어 겹침을 두고 교체한 테넌트 키는 옛 버전에서 새 키만 통합니다. 마이그레이션이 추가만 한 것이 아니면 올리기 전 백업으로 데이터베이스를 되돌린 뒤 옛 이미지를 띄웁니다.

## 백업과 복구

백업할 것은 둘이고, **같은 시점의 것을 함께** 둡니다.

| 무엇 | 어떻게 | 잃으면 |
|---|---|---|
| 데이터베이스 | `pg_dump`(또는 관리형 서비스의 시점 복구) | 테넌트·키·자격증명·메시지 기록·감사 로그 전부 |
| 키 링(`/data/dp-keys`) | 디렉터리 복사 | 아래 |

키 링만 잃었을 때(데이터베이스는 남음):

- 테넌트와 테넌트 키, 메시지 기록, 감사 로그는 그대로입니다 — 키는 해시로 두므로 키 링과 무관합니다.
- **테넌트별 채널 자격증명과 웹훅 서명 비밀값을 읽을 수 없습니다** — 다시 등록합니다(`PUT /admin/tenants/{id}/credentials/{channel}`, `PUT /admin/tenants/{id}/webhook` — 웹훅은 새 비밀값이 발급되므로 받는 쪽도 바꿉니다). API로 등록했던 공용 자격증명도 다시 등록합니다. 설정으로 주는 공용 자격증명은 시작할 때 다시 저장되므로 그대로 동작합니다.
- **발송을 기다리던 메시지는 내용을 읽을 수 없어** 평소처럼 재시도하다 `Failed`가 됩니다(`error`에 이유). 재시도가 끝나기 전(기본 약 22분)에 키 링을 되살리면 그 메시지들은 그대로 나갑니다. 이미 끝난 메시지는 내용을 보관하지 않으므로 영향이 없습니다.

복구는 데이터베이스와 키 링을 같은 시점의 백업으로 되돌리고 띄우는 것입니다. 백업 이후에 접수된 메시지와 바뀐 설정은 사라지므로, 감사 로그(「감사 로그」)로 그 사이의 관리 행위를 확인해 다시 합니다.

## 장애 대응

먼저 볼 곳은 `GET /admin/queues`(대기열), 컨테이너 로그, `GET /messages/{id}`의 `error`, `GET /admin/audit`(최근 관리 행위)입니다.

| 증상 | 확인 | 조치 |
|---|---|---|
| `oldestDueSeconds`가 계속 커짐 | 로그의 `delivery loop failed`, 데이터베이스 연결 | 발송 워커가 멈췄거나 밀림. 데이터베이스 연결을 바로잡고 재시작. 모든 인스턴스가 `WorkerEnabled=false`가 아닌지 확인 |
| `failedInLast24Hours`가 늘어남 | 실패한 메시지의 `error`, 로그의 `delivery attempt … failed` | 대개 발신 자격증명(SMTP 인증 실패, FCM 키, SOLAPI 잔액·발신번호). 해당 자격증명을 다시 등록 — 재시도를 기다리던 메시지는 새 값으로 나감 |
| 모든 요청이 `500` | 로그의 데이터베이스 오류 | 연결 문자열·비밀번호(교체 직후라면 「비밀값 교체」의 순서) |
| 한 테넌트만 `401` | `GET /admin/tenants`의 `active`, 감사 로그의 `tenant.deactivated`·`tenant.key_rotated` | 비활성화됐거나 키가 바뀜. 겹침 없이 바꿨다면 새 키를 그 서비스에 배포 |
| 한 테넌트가 `429` | 그 서비스의 호출량 | 정상 동작. 한도를 올리려면 `Sendway:RateLimit:RequestsPerMinute` |
| 웹훅이 오지 않음 | `GET /admin/queues`의 `webhooks`, 받는 쪽 응답 | 받는 쪽이 `2xx`를 돌려주는지. 전달이 끝내 실패한 이벤트는 버려지지만 결과는 `GET /messages/{id}`에 남음 |
| 테넌트 키가 새어 나감 | 감사 로그 | 본문 없이 `rotate-key` — 옛 키가 즉시 멈춤 |
| 관리자 키가 새어 나감 | 감사 로그에서 옛 키 지문(`actor`)의 행위 | 설정에서 새 키로 바꾸고 재시작(「비밀값 교체」), 그 지문으로 남은 행위를 되짚어 봄 |
| 키 링을 잃음 | — | 「백업과 복구」 |

## 비밀값 교체

Sendway가 쓰는 비밀값은 **설정(환경변수·설정 파일)으로 주는 것**과 **관리 API로 등록해 데이터베이스에 두는 것** 두 종류이고, 교체 방법이 서로 다릅니다.

| 비밀값 | 두는 곳 | 교체 방법 | 옛 값이 멈추는 시점 |
|---|---|---|---|
| 관리자 키 | 설정 `Sendway:AdminApiKey` | 값을 바꾸고 재시작 | 재시작 |
| 데이터베이스 비밀번호 | 설정 `ConnectionStrings:Sendway` | 아래 순서 | 데이터베이스에서 바꾼 즉시 |
| 공용 채널 자격증명 | 설정 `Smtp:*`, `Fcm:*`, `Solapi:*` — 또는 데이터베이스(암호화) | 설정에 있으면 값을 바꾸고 재시작, 없으면 `PUT /admin/credentials/{channel}` | 재시작 / 다음 발송 |
| 테넌트 API 키 | 데이터베이스(해시) | `POST /admin/tenants/{id}/rotate-key` | 즉시, 또는 지정한 겹침이 끝날 때 |
| 테넌트별 채널 자격증명 | 데이터베이스(암호화) | `PUT /admin/tenants/{id}/credentials/{channel}` | 다음 발송 |
| 웹훅 서명 비밀값 | 데이터베이스(암호화) | `PUT /admin/tenants/{id}/webhook`으로 다시 등록 | 다음 전달 |

### 설정으로 주는 값

설정은 프로세스가 시작할 때 읽으므로, 값을 바꾼 뒤 **재시작해야** 적용됩니다. 재시작하는 동안 접수된 메시지는 데이터베이스에 남아 있다가 이어서 발송되고, 그 사이 요청이 실패한 호출자는 같은 `Idempotency-Key`로 다시 요청하면 됩니다.

- **관리자 키** — 새 값은 충분히 긴 무작위 문자열로 만듭니다. 재시작 뒤 옛 키는 `401`입니다. 키를 쓰는 배포 스크립트나 감시 도구의 설정도 함께 바꿉니다.
- **데이터베이스 비밀번호** — 다음 순서로 합니다.
  1. 새 비밀번호를 넣은 연결 문자열을 배포 설정에 반영해 둡니다(아직 재시작하지 않습니다).
  2. 데이터베이스에서 비밀번호를 바꿉니다. PostgreSQL은 이미 열린 연결을 끊지 않으므로 실행 중인 프로세스는 계속 동작하지만, 새로 여는 연결은 실패하기 시작합니다.
  3. 곧바로 재시작합니다.

  연결 문자열에 들어가는 값이므로 새 비밀번호에는 `;`·`=`·따옴표를 쓰지 않는 편이 안전합니다.
- **공용 채널 자격증명** — 시작할 때 설정에 있는 `Smtp`·`Fcm`·`Solapi` 값이 저장된 공용 자격증명을 덮어씁니다. 설정에 그 항목이 있는 동안은 설정이 값을 소유하므로 관리 API로는 바꿀 수 없습니다(아래). 재시작 없이 바꾸고 싶으면 설정에서 그 항목을 빼고 재시작합니다 — 저장돼 있던 값이 그대로 남고, 그때부터 관리 API로 바꿉니다.

재시작 뒤에는 새 관리자 키로 `GET /admin/queues`를 불러 봅니다 — `200`이면 관리자 키와 데이터베이스 연결이 함께 확인됩니다. 옛 키로는 `401`이어야 합니다.

### 관리 API로 등록하는 값

재시작 없이 바뀝니다.

- **테넌트 API 키** — `rotate-key`의 응답에 새 키가 한 번만 실려 옵니다. 본문 없이 부르면 **옛 키는 그 순간부터 `401`입니다** — 키가 새어 나갔을 때 쓰는 방식입니다. 운영 중인 서비스의 키를 계획해서 바꿀 때는 겹침을 지정해, 그 서비스가 새 키로 옮기는 동안 두 키가 함께 통하게 합니다.

  ```bash
  # 옛 키를 24시간 더 살린다(0~604800초, 최대 7일)
  curl -X POST http://localhost:8080/admin/tenants/<tenantId>/rotate-key \
    -H "X-Admin-Key: <관리자 키>" -H "Content-Type: application/json" -d '{"previousKeyValidForSeconds": 86400}'
  # → {"apiKey": "sw_…", "previousKeyExpiresAt": "…"}

  # 그 서비스가 새 키로 옮긴 것을 확인하면 겹침을 바로 끝낸다
  curl -X DELETE http://localhost:8080/admin/tenants/<tenantId>/previous-key -H "X-Admin-Key: <관리자 키>"
  ```

  겹침 동안 옛 키로 온 요청은 그대로 처리되고, 응답에 `Api-Key-Expires` 헤더(옛 키가 멈추는 시각)가 붙으며 서비스 로그에 경고가 남습니다 — 로그에서 그 테넌트의 경고가 사라지면 옮긴 것입니다. `GET /admin/tenants`의 `previousKeyExpiresAt`은 겹침이 진행 중일 때만 값이 있습니다. 겹침 중에 다시 교체하면 그때의 키가 새 「옛 키」가 되고, 그 전의 옛 키는 즉시 멈춥니다(옛 키는 하나). 비활성화한 테넌트는 어느 키로도 통하지 않습니다.
- **공용 채널 자격증명** — 설정에 그 채널 항목이 없을 때, `PUT /admin/credentials/{channel}`(`smtp`·`fcm`·`solapi`)로 등록·교체하고 `DELETE`로 지웁니다. 테넌트별 자격증명과 같은 형식이고, 재시작 뒤에도 남습니다. 설정에 그 항목이 있으면 `409`(`managed_by_configuration`)로 거절합니다 — 그대로 받아 두면 다음 재시작 때 설정값으로 되돌아가기 때문입니다. `GET /admin/credentials`는 채널마다 값이 어디서 왔는지(`configuration`·`api`, 없으면 `null`)를 알려 주며 값 자체는 돌려주지 않습니다. `email-graph`는 공용 값을 두지 않습니다 — 공용으로 두면 모든 테넌트의 메일이 Graph로 나갑니다.
- **테넌트별 채널 자격증명** — 같은 채널에 다시 `PUT`하면 교체되고, 다음 발송부터 새 값을 씁니다. 재시도를 기다리던 메시지도 새 값으로 나갑니다.
- **웹훅 서명 비밀값** — 엔드포인트를 다시 등록하면 새 비밀값이 발급됩니다. 전달을 기다리던 이벤트도 새 비밀값으로 서명되므로, 받는 쪽의 비밀값을 함께 바꿉니다.

### 교체하지 않는 것

**Data Protection 키 링**(컨테이너 배포 시 `/data/dp-keys`)은 저장된 자격증명과 접수된 메시지 내용을 암호화하는 키입니다. 프레임워크가 주기적으로 새 키를 추가하고 옛 키는 복호화용으로 남겨 두므로 손으로 교체하지 않습니다. 이 디렉터리를 지우거나 잃으면 저장된 테넌트별 자격증명과 웹훅 비밀값을 읽을 수 없게 되어 다시 등록해야 합니다 — 데이터베이스와 함께 백업합니다.

## 감사 로그

관리 API로 상태를 바꾼 행위는 성공했을 때마다 데이터베이스에 한 건씩 남습니다. 조회(`GET`)와 거절된 요청(`400`·`404`·`409`)은 상태가 그대로이므로 남지 않습니다.

| `action` | 행위 | `subject` |
|---|---|---|
| `tenant.created` | 테넌트 생성 | 테넌트 이름 |
| `tenant.deactivated` · `tenant.reactivated` | 비활성화 · 재활성화 | — |
| `tenant.key_rotated` | 테넌트 키 교체 | 겹침을 지정했으면 옛 키가 멈추는 시각 |
| `tenant.previous_key_revoked` | 겹침을 일찍 끝냄 | — |
| `credential.set` · `credential.deleted` | 채널 자격증명 등록·교체 · 삭제(테넌트별, 또는 `tenantId`가 비어 있으면 공용) | 채널 |
| `webhook.set` · `webhook.deleted` | 웹훅 등록 · 해제 | 등록한 URL |

- **누가** — `actor`는 `admin-key:` 뒤에 관리자 키 해시의 앞 12자리입니다. 관리자 키가 하나뿐이므로 신원은 「그 키를 가진 사람」까지이고, 키를 교체하면 이 값이 바뀌어 어느 키로 한 일인지 갈립니다. 이 값으로 키를 알아낼 수는 없습니다.
- **어디서** — `remoteAddress`는 서비스가 본 연결의 주소입니다. 리버스 프록시 뒤에서는 프록시의 주소가 찍히므로, 호출한 쪽의 주소가 필요하면 배포에서 forwarded headers를 켭니다(ASP.NET Core `ASPNETCORE_FORWARDEDHEADERS_ENABLED`, 신뢰할 프록시 구성).
- **비밀값은 남지 않습니다** — 키, 자격증명 본문, 웹훅 서명 비밀값은 어느 필드에도 들어가지 않습니다.
- **기록 시점** — 변경이 저장된 뒤 같은 요청 안에서 기록합니다. 기록이 실패하면 오류 로그를 남기고 응답은 그대로 둡니다(이미 바뀐 상태를 실패로 답하면 호출한 쪽이 같은 행위를 되풀이합니다). 변경과 같은 트랜잭션은 아니어서, 그 사이에 프로세스가 죽으면 한 건이 빠질 수 있습니다.
- **보관** — 지우지 않습니다. 관리 행위는 양이 작습니다.

```bash
# 최신순, 기본 100건(최대 1000). 테넌트 하나만 보려면 tenantId
curl "http://localhost:8080/admin/audit?tenantId=<tenantId>&limit=50" -H "X-Admin-Key: <관리자 키>"
# → [{"id": "…", "occurredAt": "…", "actor": "admin-key:3f9a…", "action": "tenant.key_rotated",
#     "tenantId": "…", "subject": null, "remoteAddress": "…"}, …]

# 다음 쪽: 받은 마지막 항목의 id를 before로
curl "http://localhost:8080/admin/audit?limit=50&before=<마지막 id>" -H "X-Admin-Key: <관리자 키>"
```
